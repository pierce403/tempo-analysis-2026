# Tempo public GitHub governance and PR attack surface

Observation date: 2026-08-23
Live collection window: 2026-08-23T14:20:29Z–2026-08-23T14:23:04Z
Organization: https://github.com/tempoxyz
Method: public GitHub REST/HTML, the read-only GitHub connector, and local inspection of exact public default-branch commits

## Safety and evidentiary boundary

This was read-only public research. No pull request, issue, comment, review, reaction,
branch, tag, workflow run, release, environment, package, token exchange, or repository
setting was created or modified. No secret value was requested or accessed.

Public GitHub data does not expose private repositories, organization owners, private
teams, collaborators, deploy keys, installed GitHub Apps, custom roles, Actions
allowlists/default-token settings, secret values/scopes, runner networking or teardown,
audit logs, SSO/MFA state, or every environment setting. A source reference to
`secrets.*` or a declared write permission is a capability lead, not proof that a
particular run received a secret or effective write token.

## Executive conclusions

- GitHub returned 68 public repositories: 52 originals, 16 forks, 15 archived,
  53 active, and 48 active originals.
- All active public repositories provide the ordinary GitHub fork-to-pull-request
  contribution path. The 15 archived repositories are read-only. An outsider fork PR
  is materially different from a same-repository branch/PR created by a writer.
- 67/68 current default branches report `protected: true`. `txgen/main` alone reports
  `protected: false`. `tip.bot/main` is protected and exposes five required check
  contexts even though its ruleset-list endpoint returns no ruleset.
- All 53 active repositories' public ruleset lists were refreshed. Fifty-one inherit
  active organization branch ruleset `12500570`; only `tip.bot` and `txgen` returned
  no ruleset. Across the 64 returned records, every target is `branch`: there is no
  public active or disabled tag ruleset in the active-repository snapshot.
- The active originals contain 203 workflow files in 34 repositories. Of those,
  99 use `pull_request`, 11 use `pull_request_target`, nine use `issue_comment`, one
  uses `workflow_run`, 31 use `workflow_call`, and 14 have tag-push filters.
- Among active-original workflows, 98 files in 30 repositories reference a secrets
  context, 114 files in 30 repositories declare at least one write permission, and
  47 files in 17 repositories declare `id-token: write`. These overlap and must be
  evaluated per event/job; they are not 98 confirmed secret exposures.
- Three current workflows contain a literal self-hosted runner selection:
  `tempo/bench-e2e.yml`, `tempo/bench-replay.yml`, and
  `zones/zones-benchmark.yml`. Tempo's two are reached through a member-gated
  issue-comment benchmark dispatcher; Zones' benchmark is schedule/dispatch based.
- The public environment-detail sample from 2026-08-21 returned 40 environments
  across 12 of 18 queried high-value repositories and found required reviewers on
  only one of them. Tempo `release` and
  `release-pr` had branch-policy gates but no reviewer rule; wallet-cli and wallet-rs
  `release` had no protection rule. Today's settings-detail refresh hit GitHub's
  unauthenticated API limit, so those reviewer facts are dated, not asserted as live.
- Current source has replaced several stored GitHub App credentials with OIDC-backed
  GitHub STS: Tempo PR #7279, wallet-cli PR #99, and wallet-rs PR #525. This is a real
  reduction in long-lived credential exposure. The inspected workflow and ruleset
  source does not show a tag ruleset or an independent release-environment reviewer.

GitHub semantics used to distinguish trust boundaries:

- https://docs.github.com/en/actions/concepts/security/compromised-runners
- https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows

GitHub documents that ordinary public fork `pull_request` runs receive a read-only
`GITHUB_TOKEN` and no Actions secrets. It separately warns that a `workflow_run`
workflow may receive secrets and write tokens even when the preceding workflow did
not. Base-repository events such as `pull_request_target` and `issue_comment` require
source-specific review because they can have base-repository authority.

## Repository and pull-request ingress

The ordinary external contribution path is:

```text
outside user -> public fork -> branch in outsider fork -> PR to active Tempo repo
```

That path can propose changes to source and workflow YAML, but an ordinary
`pull_request` run from the public fork is secretless/read-only under GitHub's model.
First-time contributor workflow execution can require maintainer approval; Tempo's
exact organization approval policy is not public.

A different path exists after compromise or abuse of a collaborator, organization
member, GitHub App, deploy key, or other writer:

```text
write-capable identity -> branch inside tempoxyz repo -> same-repo PR/event
```

The fork downgrade does not protect that path. Source-declared write scopes, OIDC,
repository/environment secrets, member-only comment dispatchers, and privileged
reusable workflows must be evaluated as potentially reachable unless a separate
job/environment/identity gate proves otherwise. Branch review protects merges; it
does not automatically protect pre-merge jobs that execute same-repository PR code.

## Self-hosted runners

Current literal matches:

```text
tempo@d656ef5581505b59f1611b358e611f5a602d399e
  .github/workflows/bench-e2e.yml
  .github/workflows/bench-replay.yml

zones@7e38642cdd5a1500784fd15cf30eda5366f3350a
  .github/workflows/zones-benchmark.yml
```

Tempo's default-branch `bench.yml` receives issue comments, checks organization
membership for both PR author and commenter, resolves the PR head, and calls the
self-hosted workflows. Public history demonstrates this route operates on runner
group `tempo-bench`. This is a deliberate member boundary, not an external-fork
bypass. A compromised single member can author and comment on their own PR; runner
ephemerality, network isolation, retained state, and cross-job reach are private.

Zones' self-hosted benchmark is reached by schedule or manual dispatch, not by its
ordinary PR workflow in the current source.
