GitHub App STS boundary
-----------------------

Current gh-actions source, dd1014bf8244fded7a501e701cafab240a4f9f0e:

* actions/github-sts requests a GitHub Actions OIDC token with an audience bound
  to gh-sts.tehq.net in production (gh-sts.tehq.dev in development).
* It sends that signed OIDC token to the external host's /sts/exchange endpoint,
  with repository/organization scope and a named trust policy.
* The service returns a short-lived GitHub App installation token; the action
  masks it, persists it only as Action state/output, and attempts revocation at
  job completion.
* Trust policies live in .github/sts/*.sts.yaml in the scoped repository and
  declare GitHub permissions. The STS service and GitHub App are therefore a
  high-leverage external control-plane dependency. Ownership, deployment source,
  app installation governance, audit logging, and break-glass control are not
  established by the public client repository.

gh-sts.tehq.net is recorded here only as the third-party endpoint embedded in
Tempo's current public action. No DNS lookup, HTTP request, port scan, service
enumeration, or authentication attempt was made against it or its development
counterpart.

Current Tempo head d656ef5581505b59f1611b358e611f5a602d399e is titled
"ci: use GitHub STS for release automation instead of app credentials". Its
.github/sts/release-pr.sts.yaml grants contents:write and pull_requests:write
to jobs presenting the release-pr environment subject; source comments say it
replaces GitHub App credentials formerly stored as environment secrets. This is
a confirmed reduction in long-lived secret exposure, while concentrating trust
in the STS service, its GitHub App, environment subject matching, and policy
