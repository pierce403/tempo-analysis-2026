CAPTURED RESULTS

1. RPC-trusted Portal custody observation

  Current Zones main and #1289 authenticate header hashes and receipt roots,
  but ValidatedRpcHeader does not retain stateRoot. portal_balance calls the
  TIP-20 balanceOf method through eth_call at BlockId::hash_canonical. The
  canonical flag constrains an honest RPC server; the checker does not verify a
  returned storage/account proof against the authenticated header.

  The committed mock patch queues one arbitrary ABI-encoded U256 response and
  no header, receipt, account proof, or storage proof. The real portal_balance
  helper returns that value and consumes the one response.

  Current-main focused result:
    1 passed; 0 failed; 59 filtered out
  Current-main complete patched checker library result:
    60 passed; 0 failed
  #1289 focused result:
    1 passed; 0 failed; 76 filtered out
  #1289 complete patched checker library result:
    77 passed; 0 failed

  The tracked fresh-clone script subsequently completed with all three focused
  checks passing: current-main custody observation 1/1, #1289 custody
  observation 1/1, and #1289 omitted-account witness 1/1. Its temporary
  directory cleanup completed on exit.

  #1289 runtime code passes the returned value into the custody comparison and
  persists a verified transition when available >= derived liabilities. A
  falsely high RPC value can therefore suppress the auxiliary insolvency
  signal; a falsely low value can create a durable false divergence.

  The README explicitly makes Tempo consensus and execution trust boundaries
  and says the checker does not re-execute Tempo. Observe mode cannot affect
  execution or consensus. Classification is therefore Informational/Low:
  RPC-trusted custody observation / monitoring-integrity dependency, not a
  protocol or funds vulnerability under the stated model.

  Public prior art is adjacent: review comment r3846435907 on #1216 says a
  shared RPC compromise can forge headers for both the node and checker, and
  reply r3850112481 says the checker would be extended in a follow-up. No
  reviewed public comment specifically identified the unproved custody
  eth_call.
  https://github.com/tempoxyz/zones/pull/1216#discussion_r3846435907
  https://github.com/tempoxyz/zones/pull/1216#discussion_r3850112481

2. Omitted-account checker coverage

  The checker reads supply for every enabled token but reads account balances
  only for accounts named by decoded Transfer logs. The focused accounting
  witness starts with a derived Alice balance of 10, presents the same total
  supply with no candidate account balances, and is accepted:
    1 passed; 0 failed

  This proves the documented coverage limitation, not a normal user exploit.
  A material miss requires a balance-changing execution defect or malicious
  transition that conserves supply while omitting canonical Transfer logs.
  Ordinary modeled TIP-20 transitions name changed accounts.
