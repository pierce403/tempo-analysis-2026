WHAT THE TEST EXECUTES AND ASSERTS

The fixture calls the public Mpp::verify_session path twice concurrently. It
uses an HMAC-bound challenge, credential parsing, a real locally generated
EIP-712 voucher signature, signature verification, and ABI decoding of an
Alloy in-process mock getChannel response. A barrier makes both verification
calls capture the same pre-update channel snapshot.

Initial and final values asserted by the test:

  initial accepted cumulative authorization A0: 1,000
  initial durable spent spent0: 1,000
  unused prior authorization U=max(0,A0-spent0): 0
  presented cumulative authorization: 2,000
  accepted increment delta: 1,000
  verification/content-predicate successes N: 2
  final accepted cumulative authorization: 2,000
  final durable spent: 1,000

Both verification calls return a non-management success, so both satisfy the
same predicate used by the bundled multi-fetch example before it returns
protected content. The durable voucher advances only once and spent does not
advance. The test intentionally starts with spent=1,000 so the previous
1,000-unit authorization is fully consumed; there is no unused prior authority
that could otherwise pay for the second response.

ECONOMIC BOUND

Let:

  N = responses delivered after validations against the same old snapshot
  P = advertised price of one response
  A0 = accepted cumulative authorization before the race
  spent0 = durable spend before the race
  U = max(0, A0 - spent0), unused authorization before the race
  delta = newly accepted cumulative voucher increment

Underpayment relative to the advertised total is bounded by:

  max(0, N * P - (U + delta))

Only in the special case U=0 and delta=P does that simplify to:

  (N - 1) * P

The committed test is exactly that special case: N=2, P=1,000, U=0, and
delta=1,000, so the demonstrated underpayment relative to the two advertised
responses is 1,000 units. This is an advertised-price accounting statement,
not proof of the merchant's cost, profit, or realized financial loss.

LIMITATIONS AND SAFETY BOUNDARY

- The test executes Mpp::verify_session and recreates the bundled example's
  simple non-management success predicate. It does not launch Axum or invoke
  the example's actual HTTP handler over a socket.
- It proves the behavior for the in-memory store and the reviewed control flow;
  it does not establish that every third-party store or production integration
  is affected.
- The bundled SSE and WebSocket delivery paths debit before each event/frame
  and were not shown affected by this duplicate-delivery path.
- Applications that perform a linearizable request-cost debit before delivery
  are not shown affected.
- mpp-rs does not commit Cargo.lock at the pinned revision, so dependency
  resolution can drift. The exact compiler/tool versions and validation time
  above bound this execution; future reruns should record their resolved graph.
- No live RPC, public endpoint, production server, payment, channel, credential,
  victim key, load test, or third-party service was used.
