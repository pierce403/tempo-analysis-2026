# Work Log — 2026-08-24

## MPP streaming and agent-payment economic-security audit

- **Task**: T-012.
- **Objective**: Review the current public Machine Payments Protocol stack for ways a malicious merchant, intermediary, integration, or compromised agent could obtain excess payment, retain a costless execution option, replay settlement, exploit partial-stream cancellation, or create a payment/delivery mismatch.
- **Safety boundary**: Source, specifications, public metadata, and local dummy state only. No live payment, credential use, agent deception, authentication testing, production mutation, load test, or unrelated vendor infrastructure testing.

## Initial work plan

- Pin the current MPP specifications and Tempo-maintained Rust, TypeScript, Go, Python, proxy, wallet/agent, and example integrations.
- Map price/asset/recipient binding, payment challenge and credential lifetimes, retry/idempotency behavior, cumulative-versus-delta accounting, streaming settlement, timeout/cancellation, finality, and content-release ordering.
- Run upstream tests and add focused local model, property, or regression tests for the strongest hypotheses.
- Separate implementation defects from inherent fair-exchange limitations, and record both confirmed and falsified hypotheses with exact revisions.

## Work completed

- Pinned current MPP specifications, mppx releases/head, Rust/Go/Python SDKs, conformance tooling, Tempo reserve source, wallet/agent integrations, and examples. The exact inventory is in `recon/2026-08-24-mpp-economic-security-audit.md`.
- Modeled five independent monetary ledgers for a session: deposit, signed cumulative authorization, delivered/owed value, server-recorded consumption, and settled value. The intended safety properties are that authorization headroom remains within a small client-approved window and settlement never exceeds delivered/owed value.
- Confirmed the unavoidable plaintext-stream asymmetry: the specification requires voucher persistence and spend recording before application delivery. Existing upstream SSE/WebSocket tests pass while recording spend but emitting no application message after a post-commit failure. This is an inherent one-window free option, not by itself an implementation bug.
- Locally reproduced C-010 in the actual mppx managed SSE path at `3f73a17eeba9522d90894099635a43d6d2934cf5`: a one-unit quote and server `requiredCumulative=100` yielded a valid full-deposit voucher before any application message. The signature was independently verified; no chain or external endpoint was used.
- Locally reproduced the settlement half through exported mppx `settle()`: supplied state `highestVoucher=100`, `spent=1` caused the actual chain boundary to receive 100. Scheduled settlement calls the same helper. The behavior is also present in released mppx 0.8.15 and 0.8.19.
- Reproduced Rust parity at `fadc88c044b9f8700b58d275bb659d403b231e07`: the streaming helper produced a valid 10,000-unit full-deposit voucher from a 1,000-unit prior authorization/price. An existing upstream test accepts a 5,000,000 close amount at `spent=500` and passes it unchanged to escrow.
- Ran the mpp-rs CI-equivalent feature baseline: 1,160 library tests, 11 Stripe integration tests, five WebSocket integration tests, and 61 executed doctests passed with zero failures; 44 doctests were ignored. Green conformance did not assert the economic invariant.
- Ran the current mppx session suite after its HTML build: 648 tests passed, 13 failed, and 13 were skipped. Twelve failures were sandbox socket-bind denials; the remaining transient WebSocket case passed alone. Both focused PoCs passed, but the environment does not support a blanket green-suite claim.
- Observed the TIP-1034 native interface passively on mainnet and Moderato: native marker `0xef`, 900-second close grace, and the expected `Voucher(bytes32 channelId,uint96 cumulativeAmount)` type hash. This did not pin deployed bytecode to the reviewed source. No transaction was submitted.
- Established agent relevance in `tempoxyz/openclaw-mpp` `4e30d5677145c5e5c4aebd1c7a3d372f072db419`: it locks mppx 0.8.15, constructs the method without `maxDeposit`, and drains response streams. Its normal setup key has a seven-day, $10 total USDC limit; larger custom policies or raw keys can be broader.
- Checked prior art. mppx PR #196 publicly fixed cooperative-close high-water overcharge, and PR #510's review already warned that server values plus an uncapped default can coerce vouchers up to deposit. The raw client issue is therefore known public prior art. The retained investigation question is ordinary/scheduled high-water settlement after the close fix; no claim is made that Tempo is unaware.
- Retained C-011 in the reverse direction after two deterministic Rust PoCs. The stronger witness drove two identically signed requests through real `Mpp::verify_session`, HMAC/credential parsing, mocked `getChannel` ABI decoding, and the example's non-management-success predicate. Both succeeded while durable voucher authorization advanced from 1,000 to 2,000 once and `spent` remained zero. Static source shows the bundled multi-fetch handler returns protected content for each such success. Current head and published v0.11.0 contain the affected logic; production consumers remain unknown.
- Distinguished C-011 from prior fixes: the store update is serialized and sequential replay is rejected, but the losing atomic transition returns success after a concurrent winner advances state. The bundled SSE/WebSocket examples perform an additional atomic spend debit and were not shown affected.
- Retained C-012 as a simpler released Rust integration flaw. A full `Mpp::verify_session` PoC began with the prior 10,000-unit authorization fully consumed, authenticated a 10,000-unit page price, and accepted a valid one-unit increment while leaving only one unit available and `spent` unchanged. The bundled multi-fetch handler statically returns content for the same success predicate; current head and v0.11.0 share the pattern. This is scoped to the official example and similar verification-only consumers, not the protocol or every SDK path.
- Independently checked C-012 against the specification and adjacent GHSA history. The draft requires applications to compute request cost and atomically persist `spent += cost`; Rust SSE/WebSocket and current mppx HTTP paths do so. Public prior fixes did not address the multi-fetch omission, but private awareness and production copying are unknown.
- Modeled the opposite ambiguous-response retry case. mpp-rs rejects an exact equal-highest voucher despite the draft's idempotent-200 requirement; a caller that then signs the next cumulative voucher can authorize a second request cost absent application idempotency. Retained this only as an unnumbered integration hazard/spec-conformance defect because exact replay alone cannot increase settlement, the client does not silently perform the retry, the draft already warns about the composition, and no deployed consumer was shown.
- Did not retain separate claims for Go/Python Tempo streaming support, wallet-cli automatic-stream reachability, machine-token-only FX timing, cross-channel voucher replay, or the unproven top-up/forced-close race.
